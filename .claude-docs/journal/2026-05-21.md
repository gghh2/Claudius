# Journal — 2026-05-21

## Contexte

Très longue session entièrement consacrée à la feature « LLM local ». Partie de
la simple abstraction IA, elle a dérivé — sur preuves, log à l'appui — vers une
**refonte profonde de la façon dont les quêtes sont générées**.

## Le fil de la session

1. Abstraction multi-backend + moteur Ollama installé (Phases 0-1).
2. Outillage de debug : log sur disque de toutes les missions proposées par les PNJ.
3. Diagnostic : le LLM **sur-propose** des quêtes en permanence, produit des
   tokens absurdes, et un token foireux fait spawner des PNJ fantômes en cascade.
4. Filet de sécurité : validation sémantique des tokens.
5. Refonte du prompt de dialogue (injonction « émets un token » inversée).
6. Expérience 3B → 7B : doubler la taille du modèle **ne règle pas** la
   sur-proposition → le problème est **structurel**, pas une question de taille.
7. Décision de design (débat) : séparer le chat de la génération de quête.
8. Mise en œuvre de cette architecture (« B2 ») + mémoire de conversation.

## Décisions de conception

- **Hébergement du LLM** : auto-hébergement AWS écarté (instance `t3.medium`
  inadaptée à l'inférence ; un jeu distribué ferait payer l'inférence de tous
  les joueurs + single point of failure). Retenu : Ollama en dev, LLMUnity
  embarqué au build, OpenAI en option « bring your own key ».
- **Architecture des quêtes — « B2 »** : le chat libre ne produit JAMAIS de
  quête ; un appel d'analyse séparé décide. Raison : un seul appel qui fait
  roleplay + décision + émission de token confond les trois ; un modèle, même
  7B, sur-propose. La magie du jeu est la *conversation*, pas l'émission de
  token — et B2, en générant la quête à partir de la conversation, est en
  réalité *plus* émergent que l'ancien système qui plaquait des quêtes.
- **Récompenses** *(discuté, non implémenté)* : la récompense (crédits) doit
  être décidée par le **jeu** (barème), pas par l'IA. → BACKLOG.

## Fait

### Abstraction & outillage
- `OpenAICompatibleProvider` (logique HTTP partagée) ; `OpenAIProvider` (cloud,
  `gpt-4o-mini`) et `OllamaProvider` (local) en préréglages. `AIService` résout
  le backend depuis `PlayerPrefs` ; menu éditeur `Tools > Claudius > IA`.
- Ollama installé (modèle de dev : `qwen2.5:7b`) ; `OLLAMA_KEEP_ALIVE=-1` côté
  machine pour éviter le cold-start. Latence ~0,5-1 s — le 3090 n'est pas le goulot.
- `MissionProposalLogger` : journalise message joueur + réponse de chat +
  analyse + latence (`missions_proposees.log`, éditeur/dev uniquement).

### Architecture B2 — chat ≠ quête
- **Appel 1 (chat)** : `BuildSystemPrompt` est un prompt de roleplay PUR, sans
  machinerie de quête. Le chat ne peut structurellement plus émettre de token.
- **Appel 2 (analyse)** : `BuildQuestAnalysisPrompt` + `AnalyzeForQuest`, appel
  mono-tâche qui décide « token `[QUEST:...]` ou NONE ». Pas d'analyse sur
  l'accueil ; pas de 2ᵉ quête si une est déjà active avec le PNJ.
- Validé en jeu : 12 provocations sur 13 → NONE. Sur-proposition éradiquée ;
  demande explicite → quête cohérente avec la conversation.

### Fiabilité des tokens
- `QuestTokenDetector.IsQuestTokenValid` : validation sémantique — rejette une
  zone inconnue, un destinataire DELIVERY/TALK/ESCORT qui est un mot-zone, et un
  destinataire qui est déjà un PNJ existant (anti-doublon fantôme).
- `AIPromptConfig` (.asset des 4 rôles) : exemples réalignés (token en fin de
  message, plus de « 500 crédits », exemple de conversation sans quête).

### Mémoire & Journal
- Mémoire de conversation par PNJ (`conversationsByNpc`) : ré-aborder un PNJ
  reprend sa conversation — il se souvient. Dans la session de jeu uniquement.
- Prompt du Journal de bord refondu (anti-hallucination) : le narrateur est le
  JOUEUR (jamais un PNJ), un objet n'est pas un personnage, zéro invention.
